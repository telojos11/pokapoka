www.nba.com postMessage Origin Validation Bypass (CWE-346)

This page demonstrates a real bug: www.nba.com's global message handler accepts postMessage data from any origin, with zero validation of who sent it — it only checks that the message body contains isStorytellerMessage: true, a flag the sender fully controls. If accepted, nba.com dispatches a real DOM CustomEvent — with an attacker-chosen name and payload — on document.body, which any code on the page (not just the intended widget) can act on.

✅ Quickest, most reliable verification (single tab, ~10 seconds)

This proves the vulnerability directly against the real handler, with no popups, no second tab, and no dependency on cross-tab message delivery (which can be unreliable in browser-automation / devtools-instrumented sessions — see the note below).

  1. 1Open https://www.nba.com/ in any normal browser tab.
  2. 2Open DevTools (F12, or Cmd+Option+I on Mac) → Console tab.
  3. 3Paste this entire block and press Enter:
document.body.addEventListener('POC_ATTACKER_EVENT', e =>
  console.log('%c[INJECTED — ZERO ORIGIN VALIDATION]', 'color:#f33;font-weight:bold;font-size:14px', e.detail));

window.postMessage({
  isStorytellerMessage: true,          // the ONLY check the handler performs — fully attacker-set
  messageType: 'POC_ATTACKER_EVENT',   // arbitrary event name — not restricted to any known enum
  data: {
    marker: 'ORIGIN_VALIDATION_BYPASSED',
    note: 'This message would be identical if it arrived via postMessage from a real cross-origin attacker page — the receiving handler cannot tell the difference, because it never checks.',
    timestamp: Date.now()
  }
}, '*');

Expected result: a red [INJECTED — ZERO ORIGIN VALIDATION] line appears immediately in the console, containing the exact payload — proof the handler accepted and dispatched attacker-controlled data with no check of who sent it. This is what a real cross-origin postMessage call looks like from the receiver's point of view: the handler has no way to distinguish a same-window call from a genuinely cross-origin one, because it never inspects event.origin at all.

Note on the two-tab demo below: in testing, the cross-tab flow (open a new tab, wait, send via the returned window reference) was found to be unreliable specifically inside browser sessions instrumented by automation/devtools extensions (e.g. Claude-in-Chrome) — such tools appear to interfere with message delivery to background tabs. The underlying bug is identical either way (confirmed above); the two-tab version below simply mirrors the literal attacker/victim flow for anyone who wants to see it end-to-end in a plain, non-instrumented browser window.
